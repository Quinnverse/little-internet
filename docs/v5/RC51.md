Use Node 24 with SQLite support. Run npm ci and npm run build. Start the single-origin server with PORT=4222 DATA_DIR=./.rc-data APP_DIR=./dist npm run server. Open http://127.0.0.1:4222. ## Owner check (real hardware)

1. Enter a cabin and villa. Zoom into a desk, rotate and reset on a narrow screen.
2. Open the eye control. Enable facial movements, start the camera, then wave, smile, blink, turn, point and make a heart. Stop and confirm the browser light goes out. Repeat after backgrounding.
3. In Letters open Draw, calibrate for 30 seconds, pinch, release, hide the hand and resume. Verify two separate strokes and undo.
4. Friend two independent profiles. Take B offline. From A catch a heart, compose, choose B and confirm. Restart B, tap Boo, keep the actual letter, and place the same gift on the wall and desk. Reload. Remove only the desk instance. Verify the original and wall instance remain.
5. On cellular and Wi-Fi compare the ordinary home against combined tracking. Try denying camera permission and retrying a failed model download.

## Draft validation · 26 November

The 390×844 touch sender and the desktop recipient use separate browser storage, credentials and an actual SQLite server. A virtual camera loop of a licensed still triggered the hand model and Boo in the 3D home. The recipient was offline during confirmation, reconnected, tapped Boo, kept the letter and added desk and wall frames. On reload both 3D hotspots resolved to distinct placement IDs linked to the same saved gift. Retrying after failure produced two total letters for two intended sends. The run includes a block, not just the success animation.

Fixture: HaGRIDv2, hand_heart/00017339-9d49-4e8e-9e99-9a51e6bb8803.jpg. The QA copy was resized and letterboxed to 640×480 and repeated as MJPEG. No dataset images are included in the build or screen recordings. This covers a held pose; real motion, lighting and hand acquisition still need device validation.

To reproduce the camera path, set BASE to a local server, IMMERSIVE=1, HEART_VIDEO to an absolute MJPEG fixture, and VIDEOS and SHOTS to an evidence directory, then run node scripts/e2e-mail.mjs. Omit HEART_VIDEO to test the touch alternative. The browser records only the product UI.

Run node scripts/profile-home.mjs with RESULT pointing to a JSON file. Set PROFILE_VIDEO for a known camera input, and GL=software for the separate SwiftShader run. The profiler records the renderer actually reported by WebGL, warm rAF frame intervals (8 seconds per state), cumulative process CPU deltas and endpoint summed browser RSS. RSS includes shared pages and cached WASM. It is not GPU memory, nor proof of a leak. CPU is per logical core (100% = one core). Foreground Chromium, 960×700, DPR 1; no recording during profiling.
